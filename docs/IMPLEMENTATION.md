# 업무 인수인계 Agent 구현 기록

- 체크리스트를 매뉴얼처럼 길게 재작성하던 문제를 줄이기 위해 목록 선정·작성·내용 검토·보완이 같은 `backend/checklist_prompts.py` 기준을 사용한다. 제목은 최대 50자, 설명은 최대 500자로 검증하며 인수할 내용·핵심 확인·완료 확인의 세 줄을 권장한다. 기존 저장 항목이나 사용자의 수동 편집에 소급 적용하지 않는다. 보완 시 다른 목적의 업무를 별도 항목으로 분리할 수 있으나, 같은 업무의 준비·승인·실행·검증·기록은 하위 절차로 묶는다. 세부 필드·모든 예시를 설명에 복사하도록 요구하지 않고 원문 근거로 연결한다. 필수 승인·중요 조건·현행/미적용 구분과 근거 검증은 유지한다.

- 텍스트 청크의 저장용 `slide=0`이 AI 입력에 노출되고, 보완 응답에서는 1 이상만 허용되어 반복 실패하던 형식 불일치를 수정했다. 검색 반환 시 text의 slide를 null로 변환하고 Evidence 모델은 기존 text의 0만 null로 정규화한다. visual의 0·음수는 계속 거부하며 장표 번호와 원문 근거 검증은 유지한다. 보완 프롬프트에도 text=null, visual=실제 번호를 명시했다. 보완·추가 항목에 0이 들어오는 재현 테스트 및 백엔드 66개 테스트 통과. 실제 문서 7개의 텍스트 청크 27개와 장표 청크 5개의 반환 형식을 확인했다. 데이터 재등록·재분석은 필요 없다. 전체 AI 생성 재실행과는 구분된 형식 오류 검증이다.

- 작성 응답의 종료 사유가 `length`이면 두 업무 묶음을 즉시 한 업무씩 나누어 다시 작성한다. 각 요청은 전체 문서와 전체 업무 목록을 유지한다. 단일 업무도 잘리면 출력 한도를 6,000 → 9,000 → 12,000으로 제한적으로 조정하며, 잘린 응답은 다음 요청에 붙이지 않는다. 필터 등 다른 종료 사유와 구분하여 로그에 종료 사유·출력 한도·사용 토큰을 남긴다. 잘린 응답을 강제로 반환한 자동 테스트에서 분할 후 검증 성공, 전체 원문 유지, 재시도 상한, 불완전한 응답 미재사용을 확인했다. 백엔드 64개 테스트 통과. 기존 오류 로그에는 종료 사유가 없어 당시 실패를 출력 한도 초과로 확정하지 않는다.
- 실제 문서 7개와 기존 결과 중 출력이 큰 업무 묶음 2개를 사용한 새 작성·근거 검증·내용 검토도 통과했다. 이 실제 호출에서는 출력 잘림이 발생하지 않았으며, 자동 분할 경로는 강제 잘림 테스트로 확인했다. 이번 변경 후 전체 체크리스트 생성 재실행은 별도로 수행하지 않았다. API 재시작 및 정상 응답 확인.

- 13분 37초 후 결과 검증 실패 건의 서버 로그에서는 AI 요청이 모두 HTTP 200으로 끝났고 마지막 통합 보완 응답 이후 종료됐다. 당시 일반 예외의 상세 로그가 없어 실패 필드를 특정할 수 없다. 보완 결과의 Pydantic 형식·원문 인용·청크 검증 예외가 그대로 전파되던 경로를 수정했다. 잘못된 보완은 기존 결과에 적용하지 않고 오류 사유를 전달하여 최대 2회 재작성한다. 실패 시 검증 단계와 이유를 표시한다. 예상하지 못한 예외는 오류 번호·예외 유형·코드 위치를 기록하며 문서 내용과 응답 원문은 로그에 기록하지 않는다.
- 수정 후 실제 문서 7개를 이전 생성 결과 재사용 없이 처음부터 실행했다. 업무 13개 작성·묶음별 검증·통합 검토 지적 1건 보완·최종 검토를 476.3초에 통과했다. 결과는 진단 파일에만 기록하고 기존 34개 항목은 유지했다. 전체 회귀 테스트 61개 및 추가 최종 검토 오류 테스트를 포함한 생성 테스트 9개 통과. API 재시작 및 HTTP 200 응답 확인.

- 긴 체크리스트 응답의 HTTP 502를 줄이기 위해 체크리스트 생성은 전체 업무 목록 선정 → 업무 2개씩 상세 작성·검토 → 통합 결과 최종 검토로 진행한다. 각 상세 작성 요청에도 모든 문서와 전체 업무 목록을 전달한다. 문서별로 맥락을 분리하지 않으며, 모두 통과한 결과만 기존 저장 경로로 전달한다. 최종 검토 지적은 해당 항목의 수정·누락 업무 추가로 최대 4회 보완하고 전체 검토를 다시 수행한다. 관계없는 항목은 그대로 보존한다. 생성 요청은 최대 2개를 동시에 처리한다.
- 스트리밍은 짧은 요청에서는 동작했으나 동일한 긴 요청에서 서버 오류가 발생하여 해결책으로 적용하지 않았다. 출력 분량을 나눈 실제 검증 도구는 `python -m tools.check_checklist_live`이며, 기존 인수인계 데이터는 변경하지 않는다.
- 동일한 실제 등록 문서 7개에서 상세 작성 묶음 8개의 검증 결과를 모아 최종 통합 검토와 지적 사항 보완을 통과했다(업무 16개, 근거 136개). 재개 실행은 원문 인용을 재검사한 묶음 결과를 재사용했으므로 단일 신규 실행의 전체 소요 시간 측정은 아니다. 기존 저장된 체크리스트 34개는 변경하지 않았다. 백엔드 회귀 테스트 59개 통과. 상위 AI 서비스 장애가 앞으로 발생하지 않는다는 보장은 아니다.

- 문서 분석 방식을 `handover-content-v2`로 변경했다. PPT는 등록·재분석 단계에서 장표별 본문·표·그래프 수치·관계·주석·판독 제한을 축약 없이 정리한다. Word·Excel은 추출된 본문·표·시트·셀 위치를 그대로 보존한다. 이미지·차트 등 기존 추출 제외 영역은 제한 사항으로 명시한다.
- 체크리스트 작성과 검토에는 모든 문서의 저장된 원문·장표 정리 청크를 함께 전달하며 원본 이미지를 재전송하지 않는다. 문서별 분할 생성 실험은 적용하지 않았다. 이전 방식으로 분석한 자료는 재등록 없이 각 문서의 AI 문서 분석을 다시 실행해야 한다.
- 분석 결과 화면에서 정리된 전체 내용을 펼쳐 확인한다. `summary`는 하위 호환을 위한 처리 결과 문구이며 업무 근거로 전달하지 않는다. 새 방식의 내용 보존·잘린 응답 거부·이미지 미전송 테스트 및 관련 회귀 테스트 18개와 빌드를 통과했다. 동일 문서의 실서비스 502 해소 여부는 재분석 후 별도 확인이 필요하다.

- 체크리스트 작성·내용 검토 요청의 HTTP 502·503·504 응답은 3초 후 1회 자동 재시도한다. 해당 단계에 재시도 안내를 표시하며 실패해도 기존 자료를 유지한다. 서버 로그에는 작업·시도·상태 코드·소요 시간만 기록한다. 인증 오류는 자동 재시도하지 않는다. 관련 회귀 테스트 19개 통과. 실제 상위 AI 서버의 장애 해소를 보장하는 처리는 아니다.

- 문서 등록·분석과 체크리스트 생성·검토·확정에 더해 일정·질문·출력 흐름을 연결했다.
- LangGraph 역할: 문서 분석, 체크리스트 작성, 체크리스트 검토, 일정 계획, 업무 Q&A. 체크리스트 검토의 지적 사항은 작성 역할에 반환하며 최대 2회 수정한다.
- 인계자가 업무별 소요 업무일·선행 조건·휴일을 확인하면 AI가 순서를 제안한다. 프로그램은 날짜·기간·누락·중복·순환 조건을 검사한다. 초안 검토 후 확정하며 재조정 시 완료된 업무 날짜를 유지한다. 기본 소요 일수 1일은 사용자에게 확인받는 입력값이며 실측값이 아니다.
- 인수자는 확정된 일정의 미시작·진행 중·완료 상태를 관리한다. 현황 화면에 완료율, 기한 지난 업무, 분류별 진행률, 남은 기간, 답변 대기 건수를 표시한다.
- Q&A는 해당 인수인계 문서만 검색하고 답변의 인용을 검증한다. 대화는 사용자별로 분리하며 최근 대화와 이전 대화 요약을 사용한다. 자연어 상태 변경·캘린더 등록은 대상 확인 버튼을 누른 뒤 실행한다.
- 인수자 질문 등록과 인계자 직접 답변을 별도로 제공한다. AI 근거 부족 시 질문 내용을 게시판 입력란으로 옮길 수 있다.
- Google Calendar OAuth 로그인·PKCE·세션에 연결한 일회용 state·연결 해제·토큰 갱신·일정 등록 및 중복 일정 갱신을 구현했다. 항목별 성공·실패를 표시한다. OAuth 설정은 추후 제공받으며 실제 계정 연동은 아직 검증하지 않았다. 연결 토큰은 서버 메모리에 보관하고 재시작 후 재연결한다.
- 인계자의 성명 입력·동의 기록을 저장한 후 확정 내용과 일정의 DOCX를 출력한다. 성명 입력 방식이며 인증서 기반 전자서명은 아니다. 서명 이후 체크리스트·일정 변경 시 재확인이 필요하다. 출력의 인수 진행 상태는 출력 시점 기준이다.
- 신규 업로드의 원본을 보관하고 권한 확인 후 다운로드한다. 원본을 보관하지 않았던 기존 업로드는 재등록이 필요하다고 안내한다.
- 기존 테스트 사용자 전환 방식을 유지한다. 인계자·인수자 권한은 API에서도 검사하며 운영용 인증 연동은 포함하지 않았다.

### 검증 방법

- `python -m unittest discover -s backend -p 'test_*.py' -q`
- `python -m unittest tools.test_access tools.test_handovers -q`
- `npm test`, `npm run build`
- `node tools/check_features.cjs`: 모의 API로 일정 작성·확정·서명, 인수 상태 변경, AI 질문·게시판, 대시보드 및 역할별 화면 검증. 실제 자료를 변경하지 않는다.
- `python tools/smoke_agents.py`: 별도 임시 문서를 실제 사내 모델로 분석하여 체크리스트 작성·검토·일정·Q&A의 연결을 검증한다. API를 호출한다.
- 실제 모델 통합 실행 성공 및 Word 출력의 한글·근거·서명·페이지 번호를 렌더링하여 확인했다. Google API의 중복 갱신·부분 실패와 OAuth 세션 검사는 모의 응답으로 검증한다.
- 최종 검증: 백엔드 46개, 인수인계·접근 권한 8개, 프런트엔드 스트림 테스트 2개 통과. 배포 빌드 및 신규 화면 브라우저 회귀 검증 통과.

### 확인 순서

1. 인계자로 문서를 분석하고 체크리스트를 검토·확정한다.
2. 인수인계 일정에서 조건을 입력해 AI 초안을 생성하고 확정한다.
3. 인수자로 전환해 일정 상태와 문서 기반 질문, 인계자 질문 등록을 확인한다.
4. 인계자로 답변을 남기고 현황 화면에서 서명 및 Word 출력을 확인한다.
5. OAuth 설정 후 인수자의 Google 연결 및 선택 일정 등록을 확인한다.

- 전체 문서가 서버에 설정한 사내 LLM 엔드포인트로 전달된다. 개발·평가에는 직접 만든 문서만 사용한다.

## 2026-10-16 PPT 이미지 처리와 여러 파일 등록

- 사내 Chat Completions에 예시 슬라이드 이미지를 전달해 HTTP 200과 제목 판독을 확인했다. 키는 서버에서만 사용한다.
- PPT 등록 시 설치된 Windows PowerPoint로 슬라이드별 PNG를 만들고, AI 초안 생성 시 이미지와 텍스트·발표자 노트를 함께 보내는 코드를 연결했다. 이미지 변환 실패 시 등록을 중단하며 텍스트만 분석한 것으로 조용히 대체하지 않는다.
- 슬라이드 번호와 이미지 해석 근거를 저장하고 화면에서 해당 슬라이드를 확인하도록 연결했다. 이미지 근거는 실제 장표 존재만 검사하며 의미의 정확성을 자동 검증했다고 주장하지 않는다. 텍스트 인용은 기존처럼 원문 일치를 검사한다.
- 한 작업 공간 PPT 합계 20장, 이미지 합계 20MB까지 처리한다. 이미지로만 된 장표도 변환 대상이다. 숨김 슬라이드도 포함되며 애니메이션·영상 재생은 지원하지 않는다.
- 변환 이미지는 DB와 같은 위치의 slides 폴더에 보관한다. 문서 삭제 시 이미지도 삭제한다. 이전에 텍스트로 등록한 PPT는 이미지 분석을 위해 다시 등록해야 한다.
- 현재 변환기는 PowerPoint가 설치된 Windows 로컬 개발용이다. 서버 배포용 무인 변환기는 별도 구현이 필요하다.
- 파일 선택창에서 여러 파일을 선택할 수 있도록 변경했다. 총 10개 제한을 사전 확인하고 하나씩 순서대로 등록한다. 진행 번호·파일명, 성공 건수, 실패 파일별 사유를 표시한다. 부분 실패 시 성공한 문서는 유지한다.

최종 검증: 사용량 제한 해소 후 테스트 15개와 React 빌드 통과. PowerShell 실행 정책으로 인한 변환 실패를 수정했다. 변환 프로세스에만 ExecutionPolicy Bypass를 전달하며 시스템 정책은 변경하지 않는다. 별도 임시 DB에서 실제 PPT 5장 변환 → 사내 AI 분석 → 체크리스트 4개·이미지 근거 4개 생성 → 슬라이드 이미지 조회까지 통과했다. 이는 연결 검증이며 정확도 평가 결과는 아니다.

Edge 브라우저에서 모의 API로 여러 파일 선택, 3개 중 1개 실패 시 성공한 2개 유지, 파일별 오류 표시, 남은 등록 개수 초과 차단을 확인했다. 기존 사용자 자료는 변경하지 않았다. API와 React 개발 서버를 재시작해 변경 사항을 반영했다. 검증 스크립트: `python -m unittest backend.test_workflow backend.test_documents backend.test_slides -q`, `python tools/smoke_slides.py`, `node tools/check_multi_upload.cjs` (브라우저 스크립트의 Playwright 경로는 현재 개발 PC 기준).

실사용 오류 수정: PowerPoint가 PNG를 쓰는 동안 Vite 파일 감시가 EBUSY로 종료되어 브라우저에 Failed to fetch가 나타났다. `vite.config.js`에서 data·outputs·.artifact-build를 감시 대상에서 제외했다. 화면 서버 실행 중 별도 임시 폴더에 슬라이드 5장을 재생성한 뒤 프록시 API 응답과 Edge의 실제 슬라이드 표시를 확인했다. 사용자 업로드 3개는 이미 저장된 상태였으며 재등록하거나 삭제하지 않았다.

- 선행 업무 종료 직후 같은 날 후속 업무를 배치할 수 있다. 주말·휴일과 하루 가능 시간을 적용하고 겹치는 시간은 확정할 수 없다.
- AI 호출 전에 총 필요 시간과 가용 시간을 비교한다. 선행 관계가 순환하면 실제 업무 제목으로 경로를 표시한다.
- 기존 일 단위 일정은 기존 단위를 유지한다. 완료 항목의 날짜와 시간은 재조정해도 유지한다.
- 캘린더는 하루 내 항목을 시간 일정으로 전송한다. 여러 날에 걸친 항목은 종일 기간 표시와 일별 가능 시간 설명을 사용한다.
- 등록된 26개 항목으로 실제 AI 호출 및 날짜 검증 완료: 2026-10-19~27의 7업무일에 배치. 검증은 원본 DB를 변경하지 않았다. 기능 API 테스트 14개와 프런트 빌드 통과.

## 2026-10-20 체크리스트 검토 단계에서 선행 업무 확정

- 초안 생성 후 선행 업무 검토 Agent가 항목과 연결된 원문 인용을 비교하여 필수 선행관계를 제안한다. 단순 권장 순서, 반복 업무의 내부 절차, 외부 미결 이슈를 인계 완료의 필수 선행조건으로 연결하지 않는다.
- 관계는 항목 ID로 저장하며 제안 이유와 원문 인용을 함께 제공한다. 존재하지 않는 ID·자기 자신·중복·순환·원문에 없는 인용을 검증한다. 근거가 없으면 관계 없음이 정상 결과다.
- 카드에서 관계를 체크박스로 수정한다. 항목 삭제 시 해당 항목을 참조한 관계를 정리하고 영향을 받은 항목은 미검토로 변경한다.
- 기존 초안에는 ‘AI 선행 업무 제안’을 별도로 실행할 수 있다. 인계자가 검토를 다시 연 상태에서 실행하며 기존 관계를 다시 제안하고 검토 상태를 초기화한다. 확정 상태 및 인수자는 수정할 수 없다.
- 일정 화면은 관계를 읽기 전용으로 표시하고 서버도 체크리스트에 저장된 관계를 사용한다.
- 기존 26개 항목 실제 AI 호출은 필수 선행관계 0개를 반환했으며 유효한 결과로 확인했다. 원본 DB는 변경하지 않았다. 카드의 수정/확정 상태 렌더링 및 프런트 빌드를 확인했다.

## 공통 UI 가이드: 버튼 식별성

- 모든 실행 버튼은 기본 상태에서도 테두리·배경·내부 여백이 있어야 한다. 일반 텍스트처럼 보이는 무테두리 실행 버튼은 사용하지 않는다.
- 주요 실행은 강조색, 보조 실행은 옅은 배경과 명확한 테두리로 구분한다. 아이콘 전용 버튼에도 같은 기준을 적용한다.
- 보조 버튼은 최소 높이 34px를 확보한다. 작은 카드 버튼도 클릭 영역을 유지한다.
- hover, 눌림, 키보드 focus, 비활성 상태를 구분한다. 선택된 탭과 탐색 메뉴는 색과 테두리로 현재 상태를 보여준다.
- 새 화면과 컴포넌트에도 동일한 기준을 적용한다.

## 공통 UI 가이드: 화면 이동 위치

- 다른 화면으로 이동하는 버튼은 화면 제목 오른쪽 공통 영역(PageNavigation)에 배치한다. 카드 본문, 요약 줄, 문서 목록 하단에 분산하지 않는다.
- 이동 대상 명칭은 사이드바 메뉴명과 동일하게 사용한다. 예: ‘업무 문서로 이동’, ‘체크리스트로 이동’.
- 생성·저장·검토 확정 등 현재 화면의 작업 버튼은 해당 작업 영역에 유지한다.
- 화면 이동 버튼은 데이터 처리 중 비활성화하며, 이동 시 검토 중 입력값은 기존 workspace 상태로 유지한다.

## 공통 UI 가이드: 영역 구분선

- 큰 패널은 진한 회청색 테두리, 내부 카드와 구분선은 한 단계 옅은 색으로 구분한다.
- 색상은 CSS 공통 변수 border-panel, border-card, border-divider를 사용한다.
- 검토 완료·오류 등 상태를 나타내는 강조색은 유지하며, 모든 경계를 굵게 만들어 시각적 부담을 높이지 않는다.

## 공통 UI 가이드: 여백과 간격

- 화면 제목·설명과 본문 사이 24px, 패널 사이 24px, 패널 내부 여백 24px를 기본으로 한다.
- 같은 작업에 속한 요소는 8~12px, 작업 묶음 사이는 16~20px로 구분한다.
- 문서 등록, 예시 문서 버튼, 문서 목록은 붙이지 않고 간격을 둔다. 카드 높이를 강제로 맞추기 위한 빈 공간은 만들지 않는다.
- 좁은 화면에서는 패널 여백과 큰 영역 간격을 20px로 줄인다.
