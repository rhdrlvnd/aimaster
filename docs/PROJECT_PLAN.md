# 업무 인수인계 Agent — 프로젝트 기획

- 시작일: 2026-10-07
- 정리일: 2026-10-26
- 목적: 합의한 기능·설계·평가 기준 관리. 실행 및 검증 상태는 [구현 기록](IMPLEMENTATION.md)에서 별도로 관리한다.

## 1. 문제와 목표

업무 문서가 있어도 인계할 업무를 다시 정리하고 후임자의 반복 질문에 답하는 부담이 발생한다. 기존 업무 문서를 입력하면 AI가 체크리스트 초안을 작성하고 인계자가 검토·확정하는 서비스를 만든다. 별도의 인수인계용 원본 문서를 미리 작성하는 것을 전제하지 않는다. 개발·인사·재무·법무 등 특정 부서에 한정하지 않는다.

핵심 업무 누락과 정보 부족으로 인한 운영 이슈 대응 지연 위험을 줄이고 후임자의 업무 적응을 지원한다. 자동 장애 감지·조치 기능을 뜻하지 않는다. 개인 성장 목표는 사내 AI 역량 Lv.2에서 Lv.3이다.

## 2. 사용자와 권한

- 생성한 사용자를 인계자로 지정한다. 인계자는 문서·체크리스트·선행 업무·일정을 검토하고 확정하며 추가 질문에 답한다.
- 인수자는 확정 내용을 조회하고 업무 수행 상태를 기록하며 AI 채팅과 인계자 답변을 활용한다.
- 전체 목록의 기본 정보는 볼 수 있지만 상세 자료는 지정된 두 참여자에게만 허용한다. 서버에서 역할과 상태를 검사한다.
- 인수인계에 들어오면 현황을 먼저 표시한다. 내용 검토 완료와 인수 업무 수행 완료는 구분한다.

## 3. 입력과 처리

Word·Excel을 기본으로 PPT와 TXT·MD를 지원한다. Word·Excel은 추출된 텍스트·표·위치를 보존한다. PPT는 이미지와 텍스트·발표자 노트를 활용해 전체 내용을 축약 없이 정리하고 판독 제한을 표시한다. 추출·정리·청킹·임베딩·저장 결과를 문서별로 확인한다.

체크리스트 생성에는 저장된 모든 문서 청크와 장표 정리 내용을 전달하며 원본 이미지를 다시 보내지 않는다. 전체 업무 목록 선정 → 소수 항목씩 작성·검토 → 전체 통합 검토·보완 → 선행 업무 검토 → 저장으로 구성한다. 각 작성 요청에도 전체 자료를 유지한다. 형식·인용·문서 연결과 관계를 검증하고 통과한 결과만 저장한다.

선행 업무는 실제 인수 준비 조건이 있을 때만 제안한다. 인계자는 제안 사유·근거를 확인하고 체크리스트 검토 단계에서 관계를 수정·확정한다. 일반 운영 절차 순서나 중요도만으로 관계를 만들지 않는다.

## 4. 기능 범위

1. 문서 다중 등록·분석 결과 조회·개별/전체 재분석·삭제
2. 체크리스트 작성·근거 검증·선행 업무 제안·인계자 검토와 확정
3. 일정 초안 생성·월간 달력·드래그/날짜 선택 조정·확정
4. 인수 현황·분류별 업무 목록·인수자 수행 상태 관리
5. 문서 근거 AI 채팅·이전 대화 목록·인계자 추가 답변
6. 개인 Google Calendar 연결 및 확정 일정 등록
7. 인계자의 성명·동의 기록과 확정 내용 DOCX 출력
8. 선택한 고도화: 완료 업무를 유지하고 남은 일정을 재조정

사용자와 합의한 기능을 임의로 제외하지 않는다. 추가 아이디어는 자동으로 범위에 포함하지 않는다. Docker·스케줄러는 사용하지 않으며 일정 재조정은 인계자가 실행한다.

## 5. 일정과 결과 변경 규칙

- AI는 중요도·선후관계에 따른 순서와 이유를 제안하고 프로그램은 남은 배치 가능일에 업무 수를 가급적 균등 분배한다. 업무별 1시간·하루 최대 건수는 고정하지 않는다.
- 일정 화면의 기간과 인수인계 기간은 동일하다. 생성 성공 시 함께 저장하며 실패하면 기존 기간·일정을 유지한다.
- 시작일이 과거라면 미완료 업무는 오늘 이후 배치한다. 주말 포함 여부와 사용자가 지정한 휴일을 적용한다. 같은 날 선후행 업무가 있으면 선행 업무부터 진행한다.
- 달력은 일요일~토요일의 월간 보기다. 상세는 오른쪽 겹침 패널로 열고 날짜를 조정한다. 확정 후에도 달력을 보여준다.
- 체크리스트 재생성 성공은 이전 일정·수행 상태·서명을 초기화한다. 일정 재조정 성공은 완료 업무를 보존한 새 초안으로 교체한다. 실패하면 이전 결과를 다시 표시한다.
- 자연어 상태 변경·캘린더 등록은 사용자 확인 후 실행한다. 인계자의 추가 답변은 문서 근거와 구분하며 RAG에 자동 편입하지 않는다.

## 6. 기술 구성

React 화면, Python·FastAPI API, SQLite 업무 데이터, ChromaDB 문서 청크·벡터를 사용한다. 기본 생성 모델은 사내 API의 gpt-6.1-sol, 임베딩은 text-embedding-3-large다.

문서 분석·체크리스트 작성·체크리스트 검토·선행 업무 검토·일정 계획·업무 Q&A의 6개 역할을 분리한다. LangGraph의 역할별 처리와 서버 순서·병렬 실행 제어를 함께 사용한다. 파일 파싱·권한·저장·진행률 계산을 불필요하게 Agent로 만들지 않는다.

Google OAuth 클라이언트 설정은 서비스 공통이고 개인별로 로그인·권한 동의를 받는다. API 키만으로 개인 캘린더에 쓰지 않는다. 성명 입력·동의 기록을 서명으로 사용하며 인증서 기반 전자서명과 구분한다.

## 7. 정량 목표와 평가

| 지표 | 목표 | 기획상 예상 기준선 |
|---|---|---|
| 체크리스트 작성 시간 | 50% 이상 단축, 예상 기준 1시간 이하 | 120분 |
| 인수인계 소요 시간 | 20% 이상 단축, 예상 기준 8업무일 이하 | 10업무일 |
| 전임자 직접 확인 질문 | 40% 이상 감소, 예상 기준 12건 이하 | 20건 |
| 기한 내 인수인계 완료율 | 90% 이상 | 70% |

예상 기준선은 실제 회사 통계가 아니다. 동일 범위·완료 기준에서 직접 측정한 기존 방식과 비교한다. 작성 시간에는 생성 대기·검토·수정을 포함한다. 소요 시간은 경과 업무일 수이며 실제 투입 시간과 합산하지 않는다. 완료율은 처음 합의한 기한과 인수인계 사례 단위로 계산한다.

개인 프로젝트로 직접 제작한 예시 문서와 모의 시나리오를 사용한다. 혼자 두 역할을 실행하는 평가의 한계를 밝히고 실제 현장 성과로 표현하지 않는다. 기능 테스트 통과나 AI 생성 성공을 KPI 달성과 혼동하지 않는다. 구체적인 측정 방법은 Task 2를 따른다.

## 8. 검증할 사항과 작성 원칙

부서별 문서의 업무 누락·근거 정확성·선행 관계를 반복 확인한다. Google 실제 계정 연결부터 등록·갱신까지, 출력 문서의 레이아웃, 역할별 전체 흐름은 별도로 검증한다. 운영용 계정 인증, 토큰 보관, 장기 작업 복구는 PoC와 구분한다. 체크리스트 교체 후 이전 Google 이벤트 정리는 확인이 필요한 부분이며 양방향 자동 동기화를 약속하지 않는다.

Task 문서는 개발 전 설계 문체를 유지한다. 개발 실적은 구현 기록에 분리한다. 본문에 강조용 별표를 사용하지 않고 사용자 수정 문구·실제 경험·합의한 목표를 존중한다. 원자료 전달 경위와 내부 검토 이력은 제출 본문에 넣지 않는다.
