# Task 6 — 테스트 및 개선

## 주요 문제 해결 및 기술 리서치 (테스트 단계)

개발·인사 업무 예시 문서로 실제 생성 결과를 확인하고, 오류 로그와 자동 테스트를 함께 검토했습니다. 아래 리서치는 실제 입력·출력과 관련 코드의 조사 결과이며, 별도로 수행하지 않은 외부 자료 조사나 성능 측정은 포함하지 않았습니다.

| 이슈 구분 | 문제 상황 및 원인 | 리서치 및 해결 과정 (Reference & Solution) |
|---|---|---|
| 품질·원문 근거 | 체크리스트의 근거가 연결되지 않거나, 선행 관계의 설명과 제공된 인용문이 일치하지 않아 검증에 실패했습니다. | 검토: 문서 ID·청크 ID·인용문을 대조하고 AI가 원문을 바꾸어 쓰는 경우를 확인했습니다. 적용: 체크리스트 인용을 원문과 검증하고, 선행 관계는 기존 인용의 참조 ID를 선택하면 서버가 해당 원문을 연결하도록 수정했습니다. 없는 근거를 붙인 결과는 저장하지 않습니다. |
| 품질·항목 누락과 중복 | 묶음별 생성 과정에서 지정한 제목과 다른 제목이 반환되거나 일부 업무가 빠져 생성이 실패했습니다. | 검토: 요청한 업무 목록과 반환 항목을 비교했습니다. 적용: 업무별 식별자로 결과를 연결하고 서버에서 원래 제목과 순서를 복원합니다. 누락·중복·알 수 없는 식별자는 차단하고, 항목 배정이나 출력 길이 문제로 실패한 묶음은 더 작게 나누어 다시 작성합니다. |
| 품질·선행 관계 | 인사 문서에서 선행 관계가 나오지 않았으며, 이를 수정하면서 기존 개발 문서의 생성 결과가 나빠질 우려가 있었습니다. | 검토: 문서에 실제로 권한·환경·준비 결과가 필요한 조건이 있는지 확인했습니다. 적용: 예시 문서의 준비 조건을 보완하고 일반적인 업무 순서와 필수 선행 조건을 구분했습니다. 인사·개발 문서 모두 재생성하여 관계와 근거를 확인했습니다. 선행 관계가 없는 결과도 정상으로 허용합니다. |
| 속도·지연 | 긴 생성 요청에서 HTTP 502, 응답 잘림, HTTP 429가 발생했습니다. 단순히 대기 시간을 늘려도 정상 완료를 보장할 수 없었습니다. | 검토: 상태 코드, 응답 종료 사유, 요청 범위와 출력 분량을 확인했습니다. 적용: 전체 문서 맥락은 유지하면서 작성할 업무를 소수 항목씩 분리하고 제한된 병렬 처리를 적용했습니다. 일시적 오류는 제한 횟수만 재시도하며 429는 서버가 안내한 재시도 대기 시간을 반영합니다. |
| 예외 처리·데이터 보존 | 재생성 중 오류가 발생하면 기존 체크리스트나 일정까지 손상될 수 있었습니다. 이전 자료를 바탕으로 생성한 결과가 최신 변경 내용을 덮어쓸 가능성도 있었습니다. | 검토: 생성 시작부터 최종 저장까지의 처리 순서와 데이터 버전 검사를 확인했습니다. 적용: 최종 검증을 통과한 결과만 반영하고 실패 시 기존 데이터를 유지합니다. 작업 중 데이터가 변경되면 오래된 결과의 저장을 차단합니다. |
| 보안·권한 | 인계자와 인수자의 역할이 다르므로 화면에서 버튼을 숨기는 것만으로는 수정 권한을 통제할 수 없었습니다. | 검토: 역할별 API 권한 검사와 인수인계별 데이터 접근 경로를 확인했습니다. 적용: 서버에서 참여자 여부와 역할을 검사하고, 자연어로 요청한 변경 작업도 실행 전 확인과 권한 검사를 거치도록 구성했습니다. |


## 1. LLM 답변 품질 평가 및 개선

| 항목 | 내용 |
|---|---|
| 평가 대상 기능 | 업무 문서 기반 체크리스트 생성, 원문 근거 연결, 선행 업무 제안을 중심으로 평가했습니다. 문서 기반 질의응답은 답변 근거와 출처 확인을 중심으로 검토했습니다. |
| 평가 데이터 | 개발 업무 문서 7개와 인사 업무 문서 7개를 사용했습니다. 실제 업무 문서를 사용할 수 없어 직접 제작한 예시 문서이며, 선행 조건이 있는 사례와 부서별 업무 차이를 포함했습니다. |
| 평가 방식 | 생성된 제목·설명을 읽고 업무 구분과 분량을 확인했습니다. 인용문이 원문에 존재하는지, 선행 업무에 실제 준비 조건이 있는지, 자기 자신을 선행으로 지정하거나 순환 관계를 만드는지 확인했습니다. 실제 모델 실행과 모의 응답을 이용한 자동 테스트를 구분해 수행했습니다. |
| 개선 전 확인한 문제 | 설명이 매뉴얼처럼 길고 복잡한 항목, 업무 제목 불일치와 누락, 연결되지 않은 원문 근거, 선행 관계의 인용 불일치, 잘못된 슬라이드 번호로 인한 검증 실패가 있었습니다. |
| 개선 조치 | 제목은 50자, 설명은 500자 이내로 제한하고 ‘인수할 내용·핵심 확인·완료 확인’으로 정리했습니다. 업무 식별자와 근거 참조를 사용하고, 작성 후 항목별 검증과 전체 통합 검토를 수행하도록 구성했습니다. 텍스트 근거에는 불필요한 슬라이드 번호를 두지 않고 실제 장표 근거는 유효한 번호인지 검사합니다. |
| 개선 후 실제 생성 결과 | 기존 실제 모델 실행 기록에서 인사 문서 7개는 체크리스트 34개·선행 관계 3개, 개발 문서 7개는 체크리스트 25개·선행 관계 6개로 생성·검증·저장에 성공했습니다. |
| 대표 확인 사례 | 인사 업무에서 ‘근태 검증용 접근 권한 신청 → 개인 검증 작업공간 구성 → 근태 마감 검증 → 급여 전달 자료 검증’의 연결을 확인했습니다. 확인된 마감본이 없으면 급여 자료 작성 기능이 열리지 않는다는 문서 내용이 근거로 연결됐습니다. |
| 자동 테스트 결과 | 2026년 10월 28일 체크리스트 생성·선행 관계·API 재시도 관련 자동 테스트 31개가 통과했습니다. AI 응답을 모의 처리해 정상·오류 조건에서 프로그램이 의도대로 동작하는지 확인한 결과입니다. |
| 평가 범위와 한계 | 생성 성공과 근거 형식 검증이 모든 내용의 정확성·완전성을 의미하지는 않습니다. 독립 정답 데이터셋에 대한 정확도·Faithfulness·Relevance 평가와 LLM-as-a-Judge 점수 산정은 수행하지 않았습니다. 인계자의 최종 내용 검토를 유지합니다. |


## 2. 성능 및 비용 최적화

| 항목 | 내용 |
|---|---|
| 기존 병목 | 여러 문서의 내용을 한 번에 긴 체크리스트로 출력하면서 응답이 잘리거나 상위 AI 서버 오류가 발생했습니다. 문서 분석 이후에도 원본 이미지를 다시 전달하는 방식은 같은 자료를 반복 처리하는 부담이 있었습니다. |
| 개선 전략 | 문서 등록 단계에서 전체 내용을 정리해 저장하고 체크리스트 생성에는 저장된 텍스트를 사용합니다. 전체 업무 목록을 먼저 만든 뒤 소수 항목씩 작성하고, 마지막에 전체 결과를 통합 검토합니다. |
| 맥락 유지 방식 | 문서를 서로 나누어 전달하지 않고 각 작성 요청에 전체 문서 내용과 전체 업무 목록을 함께 전달합니다. 문서 간 조건을 파악할 수 있도록 하면서 한 번에 생성할 출력 분량을 줄였습니다. |
| 적용 기술 | 비동기 요청, 업무 2개 단위의 생성 묶음, 최대 2개 묶음의 동시 처리, 출력 한도 초과 시 묶음 세분화, HTTP 오류별 제한 재시도를 적용했습니다. |
| 반복 처리 감소 | PPT 이미지는 문서 분석 단계에서 읽고 이후 체크리스트 생성에는 저장된 정리 내용을 활용합니다. 문서 검색용 임베딩도 저장된 벡터를 활용하며, 동일 문서를 질문할 때마다 처음부터 다시 만들지 않습니다. |
| 실제 처리 결과 | 기존 실제 모델 성공 실행에서 인사 문서 7개는 약 247초, 개발 문서 7개는 약 296초가 걸렸습니다. 생성과 검증을 포함한 각 실행의 소요 시간이며 평균 응답 시간은 아닙니다. 개발 문서의 앞선 실행에서는 429 오류로 실패한 기록도 있습니다. |
| 비용·성능 해석 | 동일 조건의 개선 전후 반복 측정은 수행하지 않아 속도 향상률이나 비용 절감률을 제시하지 않았습니다. 전체 맥락을 반복 전달하고 검토 요청을 추가하므로 호출 수와 입력 토큰이 늘 수 있습니다. 이번 개선은 긴 요청의 안정적인 완료와 결과 검증에 우선순위를 두었습니다. |


## 3. 예외 처리 및 가드레일

| 항목 | 내용 |
|---|---|
| 차단 대상 | 없는 문서·청크를 참조한 인용, 원문에서 확인되지 않는 인용문, 누락·중복된 업무 식별자, 유효하지 않은 슬라이드 번호, 자기 참조·순환 선행 관계, 권한 없는 변경, 오래된 데이터 버전으로 저장하는 요청을 차단합니다. |
| 탐지 방식 | Pydantic 기반 응답 형식 검사, 원문·근거 식별자 대조, 업무 목록 일치 검사, 선행 관계 그래프 검사, 서버의 참여자·역할·데이터 버전 검사를 사용합니다. |
| 잘못된 AI 결과 대응 | 오류 내용을 반영해 제한 횟수 내에서 보완을 요청합니다. 최종 검증에 실패하면 부분 결과를 정상 초안으로 저장하지 않고 실패 단계와 이유를 안내합니다. |
| API 오류 대응 | 공통 요청 처리에서 429·502·503·504와 같은 일시적 오류는 제한적으로 재시도합니다. 인증 오류는 같은 요청을 반복하지 않습니다. 재시도 후에도 실패하면 기존 자료를 유지합니다. |
| 자연어 작업 실행 보호 | 대화 중 일정 완료 처리 등 변경을 요청해도 바로 실행하지 않고 대상과 변경 내용을 확인받습니다. 실행 시 서버에서 권한과 최신 상태를 다시 검사합니다. |
| 자동 테스트로 확인한 내용 | 존재하지 않는 인용 차단, 무관한 근거 참조 차단, 순환 관계 거부, 누락·중복 식별자 거부, 통합 검토 실패 시 부분 결과 반환 방지, 재시도 횟수 제한, 429 대기 시간 반영, 인증 오류 재시도 방지를 확인했습니다. |
| 검증 범위 | 이번 재실행에서 통과한 31개는 생성·선행 관계·통신 오류 테스트입니다. 권한과 자연어 실행 확인은 별도 테스트 코드로 관리하고 있습니다. 프롬프트 인젝션·시스템 프롬프트 노출 공격에 대한 정량 방어 시험은 수행하지 않았으므로 방어 성공률을 기재하지 않았습니다. |


## 4. 기타 문제 해결 사례

### 4.1 재생성 중 기존 결과가 새 결과처럼 보이는 문제

- 문제: 초안 생성 중에도 이전 체크리스트 26개가 표시돼 생성이 끝난 것으로 오해할 수 있었습니다.
- 개선: 재생성 중에는 이전 결과를 숨기고 진행 상태를 표시하도록 변경했습니다. 실패하면 기존 결과를 다시 보여주고, 성공하면 검증된 새 결과로 교체합니다.

### 4.2 여러 문서의 분석 진행 상태를 구분하기 어려운 문제

- 문제: 문서를 여러 개 등록하면 마지막 문서의 과정만 보이거나, 처리 중인지 멈춘 것인지 파악하기 어려웠습니다.
- 개선: 문서별 진행 상태와 완료 결과를 구분하고 선택한 문서의 과정을 확인하도록 구성했습니다. 문자 수·청크 수·벡터 수는 실제 처리 결과를 표시합니다.

### 4.3 근거 인용과 문서 전체 내용이 혼동되는 문제

- 문제: 인용문 아래에 문서 전체가 길게 표시돼 어떤 내용이 체크리스트의 근거인지 알기 어려웠습니다.
- 개선: 선택한 체크리스트와 직접 연결된 인용문을 중심으로 표시하고, 전체 문서는 같은 화면의 원본 다운로드로 확인하도록 정리했습니다.

### 4.4 일정 재생성과 인수인계 기간이 맞지 않는 문제

- 문제: 체크리스트를 다시 생성해도 이전 일정이 남거나, 일정 화면에서 바꾼 기간과 인수인계 기간이 달라 검증 오류가 발생했습니다.
- 개선: 체크리스트 재생성 성공 시 이전 일정과 관련 상태를 초기화하도록 했습니다. 일정 생성 성공 시 인수인계 기간과 일정을 함께 반영하고, 실패하면 기존 기간과 일정을 유지합니다.

### 4.5 선행 관계 수정 후 다른 업무 문서의 동작 확인

- 문제: 인사 문서의 선행 관계를 개선하는 과정에서 개발 문서의 정상 동작까지 달라질 수 있었습니다.
- 개선: 원본 데이터를 복제한 별도 검증 환경에서 두 문서 세트를 각각 생성했습니다. 항목·관계·원문 근거를 확인하고 원본 데이터가 변경되지 않았는지도 검사했습니다. 특정 부서의 항목 수나 관계 수를 코드에 고정하지 않았습니다.
