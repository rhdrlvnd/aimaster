# 업무 인수인계 Agent — 10분 제한 발표 대본

## 표지

안녕하세요. 업무 인수인계 Agent를 개발한 이다운입니다.


## 01. 프로젝트 개요

인수인계에 필요한 정보는 운영 매뉴얼과 업무 정의서 등 여러 문서에 흩어져 있습니다. 전임자는 이를 다시 읽으며 전달할 내용을 정리해야 하고, 후임자는 무엇부터 익혀야 하는지 파악하기 어렵습니다.

사용 흐름은 다음과 같습니다. 인계자가 문서를 등록하면 Agent가 체크리스트와 원문 근거, 선행 업무를 제안합니다. 인계자가 검토·확정하면 일정으로 연결하고, 인수자는 진행 상태를 기록하거나 문서 기반 Q&A로 필요한 지식을 확인합니다.

실제 모델 실행에서는 분석이 끝난 인사 문서 7개로 체크리스트 34개를 약 4분 7초에 생성하고 검증했습니다. 문서 분석과 사람의 검토 시간은 제외한 결과입니다.

인수인계 테스트에서는 기존에 보통 14일 걸리던 기간이 10일로, 달력일 기준 약 29% 차이가 났습니다. 테스트한 3건은 모두 기한 안에 마쳤지만, 사례가 적어 추가 검증이 필요합니다.

인수자의 질문 20건 중 14건, 70%는 AI가 문서 근거로 답했고, 전임자의 추가 답변이 필요한 질문은 30%였습니다.

정리하면, 기존 문서로 AI가 초안을 만들기 때문에 전임자는 처음부터 정리하는 부담을 줄이고 검토에 집중할 수 있습니다.


## 02. 기술 아키텍처

사용자 화면은 React, API 서버는 FastAPI로 구성했습니다. 서버가 사용자 권한을 확인하고, LangGraph와 서버 로직으로 필요한 Agent를 호출합니다.

체크리스트·일정·대화 같은 업무 데이터는 SQLite에 저장합니다. 문서 청크와 임베딩은 ChromaDB에 저장하고 Q&A 검색에 사용합니다. 확정 업무는 Google Tasks와도 연동합니다.

체크리스트 생성에는 두 가지 워크플로 패턴을 적용했습니다.

첫 번째는 Orchestrator–Workers입니다.

먼저 작성 Agent가 전체 문서를 참고해 업무 목록을 선정합니다. 어떤 업무를 뽑을지는 LLM이 판단하고, 서버가 목록을 검증해 두 항목씩 묶어 배정합니다. 동시에 실행하는 묶음은 최대 두 개입니다.

예를 들어 업무가 6개라면 세 묶음으로 나누고, 각 Worker가 맡은 업무의 설명과 근거를 작성합니다. 각 요청에는 전체 문서와 전체 업무 목록을 함께 전달합니다. 문서가 아니라 작성할 업무를 나누는 것입니다.

서버는 업무 식별자로 응답을 연결하고 순서대로 통합합니다.

두 번째는 Evaluator–Optimizer입니다. 작성 결과를 평가하고 피드백을 반영해 보완합니다.

작성 Agent가 초안을 만들면 코드가 형식과 원문 연결을 검사합니다. 이어서 검토 Agent가 누락·중복·근거 없는 설명을 확인하고, 문제가 있으면 작성 Agent가 구체적인 지적 사항을 받아 다시 작성합니다. 같은 모델을 사용하지만 프롬프트와 판단 기준은 구분했습니다.

묶음을 합친 뒤에는 전체 문서와 다시 비교합니다. 묶음별 작성은 최초 작성을 포함해 최대 다섯 번, 통합 검토의 보완은 최대 다섯 번으로 제한합니다. 보완한 결과도 다시 검토하고, 최종 실패 시 기존 자료를 유지합니다.

마지막으로, 판단은 AI가 하고 확인은 서버가 맡습니다. 서버는 Pydantic으로 응답 구조를 확인하고, 별도 코드로 문서·청크·장표 연결과 인용문, 선행 관계를 검사합니다.

일정은 AI가 순서를 제안하고 서버가 기간·휴일·선행 조건에 맞춰 배치합니다. 최종 내용은 인계자가 확인하고 확정합니다.


## 03. 핵심 기술 과제와 해결 과정

가장 어려웠던 점은 여러 문서의 조건을 놓치지 않으면서 긴 체크리스트를 안정적으로 만드는 것이었습니다. 이를 세 가지 설계로 해결했습니다.

첫째, 많은 업무를 한 번에 작성하면 응답이 잘렸고, 별도로 502 서버 오류와 429 요청 제한도 발생했습니다. 문서별로 나누면 다른 문서의 준비 조건을 놓칠 수 있어, 전체 문서는 공유하고 작성할 업무만 나눴습니다. 출력 분량과 재작성 범위는 줄지만 입력 토큰이 늘어나는 점은 감수했습니다. 비용 절감보다 문서 간 조건을 유지하면서 생성을 완료하는 데 우선순위를 두었습니다.

둘째, 응답 형식이 맞더라도 내용이 충분하지 않을 수 있었습니다. 필수 항목과 인용문이 있어도 중요한 업무가 빠지거나 변경 예정 내용을 현행 절차처럼 설명할 수 있습니다.

그래서 형식 검사에 더해 검토 Agent가 원문과 초안을 비교하게 했습니다. 단순 재시도와 달리 발견한 문제를 피드백으로 전달한다는 점이 핵심입니다. 대신 검토 호출과 대기 시간이 늘어나고, 검토 Agent도 오류를 놓칠 수 있다는 한계가 있습니다.

셋째, AI가 원문을 바꿔 인용하거나 장표 근거를 잘못 연결하는 경우가 있었습니다. 코드가 공백과 줄바꿈 차이를 정리한 뒤 인용문이 원문에 그대로 포함돼 있는지 검사하고, 장표 연결이 잘못된 경우도 저장 전에 차단했습니다. 선행 관계는 AI가 근거 ID를 고르고 서버가 원문을 연결합니다.

결과는 개발 중 실제 모델 실행 로그로 확인했습니다. 한 번에 생성하던 방식은 네 번 모두 502 오류로 실패했지만, 업무를 나눈 뒤에는 여섯 번 모두 검증과 저장까지 마쳤습니다.

같은 여섯 번에서 검토 Agent가 누락·중복·근거 문제 26건을 지적해 해당 항목을 보완했습니다. 원문과 다른 인용이나 잘못된 장표 근거 7건은 코드가 저장 전에 찾아 다시 쓰게 했습니다. 해당 여섯 번의 최종 저장 결과에서는 원문 불일치가 0건이었습니다.

저장 성공률 100%는 이번 여섯 번의 개발 실행에서 확인한 결과입니다. 검사를 통과했다고 업무 누락이 없거나 내용이 모두 정확하다는 뜻은 아닙니다.

이번 구현으로 작성 범위는 나누되, 판단에 필요한 문서 맥락은 유지해야 한다는 점을 배웠습니다. 또 AI의 내용 검토, 코드의 검증, 사람의 최종 확정은 각각 잡아내는 오류가 달라서, 역할을 나누는 것이 중요했습니다. 내용의 정확성은 인계자가 최종 확인하도록 했고, 앞으로는 부서별 평가 세트로 누락률과 답변 정확도, 사람의 검토 시간을 함께 측정하겠습니다.


## 마무리

업무 인수인계 Agent는 전체 문서를 바탕으로 업무를 분할 작성하고, 평가와 보완을 거쳐 근거를 확인할 수 있는 초안을 제공합니다. 이를 일정과 업무 질문으로 연결해 인수인계 준비와 수행을 지원했습니다.
