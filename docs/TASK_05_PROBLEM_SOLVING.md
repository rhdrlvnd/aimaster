- 범위: Task 5의 ‘주요 문제 해결 및 기술 리서치’ 교체용 본문
- 작성 근거: 사용자가 실제 화면·생성 결과·오류를 확인하며 제기한 질문과 현재 코드. 외부 문헌을 조사한 이력이나 성능 개선 수치를 임의로 추가하지 않는다.


## 제출용 본문

개발 중 실제 문서를 등록하고 생성 결과와 화면을 확인하면서 문제를 발견했습니다. 단순히 오류를 없애는 것뿐 아니라 인수인계 목적에 맞는 결과인지, 사용자가 내용을 이해하고 검토할 수 있는지를 기준으로 수정 방향을 정했습니다. 아래 조사 과정은 실제 입력·출력, 오류 로그와 관련 코드의 검토를 중심으로 작성했습니다.

| 이슈 구분 | 문제 상황 및 원인 | 리서치 및 해결 과정 (Reference & Solution) |
|---|---|---|
| 문서 분석 방식 | PPT에서 글자만 추출하면 그래프·도형에 담긴 내용을 놓칠 수 있었습니다. 또한 문서 분석 후 체크리스트 생성 때 원본 이미지를 다시 전달하는 방식이 필요한지 의문이 있었습니다. | 검토: ‘슬라이드를 이미지로 읽으면 어떨까?’, ‘이미 읽은 내용을 정리해 보내면 되지 않을까?’라는 관점에서 문서 분석과 체크리스트 입력 경로를 확인했습니다. 적용: PPT 이미지는 문서 등록·분석 단계에서 전체 내용을 정리하고, 이후 생성에는 저장된 정리 내용을 사용하도록 변경했습니다. Word·Excel도 추출 내용을 요약으로 대체하지 않고 보존했습니다. |
| 체크리스트 분량·업무 구분 | 생성된 체크리스트가 세부 절차와 조건을 길게 나열해 매뉴얼처럼 무거웠고, 실제로 무엇을 인수받아야 하는지 파악하기 어려웠습니다. | 검토: 생성 결과를 직접 읽고 하나의 업무가 과도하게 나뉘거나 설명에 세부 사항이 반복되는지 확인했습니다. 적용: 같은 업무의 연속 절차는 묶고 제목은 50자, 설명은 500자 이내로 제한했습니다. 설명은 ‘인수할 내용·핵심 확인·완료 확인’으로 정리하고 자세한 절차는 원문 근거로 확인하도록 작성·검토 기준을 맞췄습니다. |
| 긴 생성 요청·맥락 유지 | 초안 생성 중 502와 응답 미완성 오류가 반복됐습니다. 요청을 나눌 경우 문서 간 내용을 함께 파악하지 못할 수 있다는 우려도 있었습니다. | 검토: 상태 코드·응답 종료 사유와 요청에 포함된 자료를 확인했습니다. 적용: 문서를 나누는 대신 작성할 업무를 소수 항목씩 나눴습니다. 각 요청에도 전체 문서와 전체 업무 목록을 전달하고 마지막에 통합 검토를 수행했습니다. 실패한 묶음은 더 작게 재작성하며 검증에 실패하면 기존 초안을 유지합니다. 상위 서버의 502 내부 원인을 확정하거나 장애가 완전히 사라졌다고 판단하지는 않았습니다. |
| 선행 업무 제안·근거 검증 | 개발·인사 문서에서 기대한 선행 관계가 나오지 않거나 ‘관계 근거가 제공된 원문 인용에 없음’ 오류가 발생했습니다. 관계를 무조건 많이 만드는 것도 적절하지 않았습니다. | 검토: 실제 준비 조건이 문서에 있는지, 일반 운영 순서를 선행 조건으로 오해하는지, AI가 인용문을 바꿔 쓰는지 확인했습니다. 적용: 준비 조건이 있는 예시 문서를 보완하고 프롬프트는 권한·환경·준비 결과가 필요한 경우만 연결하도록 했습니다. AI가 기존 인용의 참조 ID를 선택하면 서버가 원문을 연결하도록 변경했습니다. 인사 문서와 개발 문서를 각각 재생성해 검증했으며, 관계가 없는 결과도 정상으로 허용했습니다. |
| 일정 배치 방식 | 일정이 업무별 고정 시간이나 하루 처리 개수에 묶여 원하는 인수인계 방식과 맞지 않았습니다. 일정 시작일이 과거일 때 처음 며칠이 비어 보이는 이유도 명확하지 않았습니다. | 검토: ‘전체 업무를 남은 기간에 어느 정도 균등하게 나누자’는 요구에 맞춰 날짜 배정 로직을 확인했습니다. 적용: AI는 중요도·선행 조건에 따른 순서와 이유를 제안하고 프로그램은 남은 배치 가능일에 업무 수를 분배하도록 변경했습니다. 시작일이 과거이면 오늘 이후로 배치하고 완료 업무는 재조정 시 유지합니다. 업무 수의 균등 배분과 실제 업무량의 균등 배분은 구분합니다. |
| 분석 진행·재생성 화면 | 문서를 읽는 중인지 멈춘 것인지 알기 어려웠고 마지막 문서의 결과만 보이는 문제가 있었습니다. 재생성 중 이전 항목 수가 표시돼 새 결과로 오해할 수도 있었습니다. | 검토: 여러 문서를 등록하고 메뉴를 이동하며 처리 상태와 표시 내용을 확인했습니다. 적용: 문서별 진행·결과를 구분하고 실제 문자·청크·벡터 수를 표시했습니다. 한 번에 선택한 문서의 과정을 보여주며, 같은 작업 공간의 메뉴 이동 중에도 진행 상태를 유지하도록 했습니다. 재생성 중에는 이전 결과를 숨기고 실패하면 복원하도록 변경했습니다. |
| 원문 근거의 가독성 | 인용문 아래에 문서 전체가 ‘본문 1, 본문 2’ 형태로 표시돼 어느 부분이 체크리스트를 뒷받침하는지 알기 어려웠습니다. 전체 본문은 원본 다운로드와도 역할이 겹쳤습니다. | 검토: 근거 확인 화면에서 직접 인용과 참고용 전체 문서가 혼동되는지 확인했습니다. 적용: 선택한 체크리스트 제목과 연결된 인용문을 우선 표시하고 근거 화면의 전체 본문을 제거했습니다. 전체 내용은 원본 다운로드로 확인하도록 하고 PPT 근거 장표 확인은 유지했습니다. |
| 역할에 맞는 질문 화면 | 인계자와 인수자에게 같은 질문 화면을 제공하면 인수자는 대화하기 어렵고 인계자는 답변할 요청을 찾기 어려웠습니다. 드롭다운만으로는 이전 대화의 존재도 알아보기 어려웠습니다. | 검토: 인수자는 AI와 대화하고 인계자는 넘어온 질문에 답한다는 실제 역할을 기준으로 화면 흐름을 다시 정리했습니다. 적용: 인수자는 대화 목록과 채팅 화면을, 인계자는 답변 대기·완료 질문 목록을 사용하도록 분리했습니다. 추가 확인 요청에 원 질문·AI 답변·근거를 연결하고 인계자의 답변을 원래 대화에서도 확인하도록 했습니다. |


## 내부 근거 메모 — 제출 본문 제외

- 문서 분석: 사용자 ‘요약 하는게 아님’, ‘체크리스트 만들때는 이미지 대신 이러한 정리된 내용들을 보내야지’. 코드 backend/rag.py, backend/slides.py.
- 분량: 사용자 ‘프롬프트를 자세히 쓰던가 해서 수정해봐. 내가봐도 이건 너무 무거워.’ 코드 backend/checklist_prompts.py.
- 맥락: 사용자 ‘나누게 되면 서로간의 내용을 파악해서 중요한걸 뽑을때 문제가 있을수 있는건 아냐?’ 코드 backend/checklist_generation.py, backend/test_checklist_generation.py.
- 선행 업무: 사용자 인사·개발 문서 관계 누락 질문, 인용 불일치 오류 전달, ‘개발쪽 문서 잘되던데 망가지면 안되니까’. 코드 backend/dependencies.py. 실모델 성공 기록은 인사 34항목·3관계, 개발 25항목·6관계이며 독립 평가셋 성능이 아니다.
- 일정: 사용자 ‘총 체크리스트 개수를 남은 기간 어느정도 균등하게 분배’, ‘왜 첫날부터 일정이 생기지않고 3째날부터’. 코드 backend/scheduling.py.
- 진행: 사용자 ‘멈춘건지 아직 읽고 있는건지’, ‘마지막 문서의 프로세스만’, ‘26개가 벌써 나온 이유’, ‘페이지로 이동’. 코드 src/hooks/useWorkspace.js, src/documentProgress.js 및 관련 화면.
- 근거: 사용자 ‘모두 이 체크리스트의 근거가 되는거야?’, ‘본문 1 이런식으로 나눠서 보여줘야해?’. 코드 src/components/documents/EvidenceDrawer.jsx.
- 질문 화면: 사용자 ‘전임자는 ai가 넘겨준 질문들을 대답해주는 화면’, ‘후임자는 ai랑 챗봇 형태’, ‘이전 대화가 있었다는것도 모를거같아’. 코드 src/components/features/QuestionsPanel.jsx, QuestionInbox.jsx.

사용자가 문제를 발견하고 요구·검토 방향을 제시한 사실과 구체적인 코드 수정·로그 분석의 수행 주체는 구분한다. 면접에서는 AI 개발 도구와 함께 구현했다는 사실을 유지하고 직접 설명할 수 있는 부분만 본인 기여로 구체화한다.
